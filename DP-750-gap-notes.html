Compute Types & Configuration

Setup 15–20%
Critical Databricks Compute Types — Know Every One ▾ expand
TypeUse CaseKey Trait
Job computeScheduled ETL, batch pipelinesAuto-terminates after job. Cheapest for production.
All-purpose (classic)Dev, interactive notebooksStays running. Expensive if left idle. Never use for prod ETL.
ServerlessNo-config compute, fast startupDatabricks manages infra. You pick cores only. No config needed.
SQL WarehouseBI queries, SQL analytics, dashboardsOptimised for SQL. Classic or serverless variant. Use for AI/BI Genie.
Shared computeMulti-user, cost-effective devMultiple users share one cluster. Limited to SQL & Python. No arbitrary installs.
Cluster poolsReduce startup latency for job clustersPre-warmed VMs waiting. Job cluster borrows from pool — starts in seconds.
The exam loves "which compute type should you use?" scenarios. Job compute = scheduled/ETL every time. Serverless = when no config is required. All-purpose = ONLY interactive dev. Never recommend all-purpose for production scheduled pipelines.
Photon acceleration is a cluster feature — not a separate compute type. It must be enabled on a supported node type (Standard_D/E series). It does NOT accelerate RDD-level code — only SQL and DataFrame API calls.
Performance settings to know
  • Autoscaling — min/max workers. Databricks adds/removes workers based on load. Set min ≥ 1 to avoid cold cluster.
  • Auto-termination — idle minutes before shutdown. Always set on all-purpose clusters to avoid cost bleed.
  • Node type — memory-optimised for large joins/caches, compute-optimised for CPU-heavy transforms, GPU for ML.
  • Databricks Runtime (DBR) — versioned Spark + libraries. DBR ML = includes ML frameworks. Match DBR to your Spark version requirements.
Medium Library Installation Scopes ▾ expand
  • Notebook-scoped — %pip install package inside a cell. Only applies to that notebook session. Use for quick experimentation.
  • Cluster-scoped (init scripts) — runs on every node at startup. Use for C libraries or packages needed by all notebooks on that cluster.
  • Workspace libraries — uploaded to workspace, then attached to cluster via UI. Good for custom .whl files.
  • Policy libraries — defined in cluster policy, auto-installed on any cluster using that policy.
If the question says "all notebooks on the cluster need the library" → cluster-scoped / init script. If "just this one notebook" → %pip install.

Unity Catalog — Deep Dive

Setup 15–20%
Critical Unity Catalog: Hierarchy, Objects & DDL ▾ expand
Microsoft Purview governs data across Azure. Unity Catalog does the same but is SQL-native and embedded in Databricks. One metastore per Azure region, attached to multiple workspaces.
The 3-level namespace

catalog.schema.table — every object reference uses this format. You cannot query schema.table alone.

SQL
-- Full hierarchy creation
CREATE CATALOG IF NOT EXISTS bronze_prod;
CREATE SCHEMA IF NOT EXISTS bronze_prod.raw_data;

-- Managed table (UC owns the data files)
CREATE TABLE bronze_prod.raw_data.events (
  event_id BIGINT NOT NULL,
  event_ts TIMESTAMP,
  payload  STRING
) COMMENT 'Raw event stream from Event Hubs';

-- External table (you own the ADLS path)
CREATE TABLE bronze_prod.raw_data.ext_events
LOCATION 'abfss://raw@mystg.dfs.core.windows.net/events/'
AS SELECT * FROM parquet.`abfss://raw@mystg.dfs.core.windows.net/events/`;

-- Volume (for files, not tables)
CREATE VOLUME bronze_prod.raw_data.landing_files;

-- Materialized view (stores precomputed result)
CREATE MATERIALIZED VIEW gold_prod.sales.mv_daily_totals
AS SELECT date_trunc('day', ts) AS day, SUM(amount) AS total
   FROM silver_prod.sales.orders GROUP BY 1;
Managed vs External is a top exam topic. Managed = DROP TABLE deletes the data. External = DROP TABLE removes the metadata only, data remains in ADLS. Use External when data is shared with other tools (ADF, Synapse).
Volumes — new concept for DP-750
  • Volumes store files, not tables. Think of them as UC-governed folders in ADLS.
  • Managed volumes — UC manages the path. External volumes — you specify the ADLS path.
  • Access via /Volumes/catalog/schema/volume_name/file.csv — use in COPY INTO, Auto Loader, etc.
Foreign Catalogs
  • Connect to external data sources: PostgreSQL, MySQL, Iceberg REST catalog, Delta Sharing.
  • Created via connections in UC — define connection → create foreign catalog pointing to it.
  • Read-only by default. Used to query external databases without moving data.
AI/BI Genie — configure for data discovery
  • Genie uses table/column descriptions to understand your data for natural language queries.
  • Add descriptions via: ALTER TABLE t ALTER COLUMN c COMMENT 'description';
  • Configure Genie instructions in the Databricks workspace UI — point it at your Unity Catalog tables.

Security & Governance — New Patterns

Secure & Govern 15–20%
Critical GRANT / REVOKE — The Full Permission Chain ▾ expand
The #1 mistake on permission questions: granting SELECT on a table is NOT enough. The user also needs USE CATALOG and USE SCHEMA or they cannot navigate to it.
SQL
-- Minimum grants for a read-only analyst:
GRANT USE CATALOG ON CATALOG gold_prod TO GROUP analysts;
GRANT USE SCHEMA  ON SCHEMA gold_prod.sales TO GROUP analysts;
GRANT SELECT      ON TABLE gold_prod.sales.orders TO GROUP analysts;

-- Grant on all tables in schema (wildcard-style)
GRANT SELECT ON ALL TABLES IN SCHEMA gold_prod.sales TO GROUP analysts;

-- Revoke
REVOKE SELECT ON TABLE gold_prod.sales.orders FROM GROUP analysts;

-- Service principal access (for pipelines)
GRANT SELECT ON TABLE bronze.raw.events TO `app-id-of-service-principal`;
PrivilegeApplies toWhat it allows
USE CATALOGCatalogNavigate into the catalog
USE SCHEMASchemaNavigate into the schema
SELECTTable/ViewRead data
MODIFYTableINSERT, UPDATE, DELETE
CREATE TABLESchemaCreate tables in schema
ALL PRIVILEGESAnyFull control
Critical Row Filters & Column Masks — Brand New Pattern ▾ expand

Both are implemented as SQL functions applied to tables. This is entirely new — nothing equivalent exists in ADF/Synapse at this level.

Row Filters — control which rows users see
SQL
-- Step 1: Create filter function
CREATE FUNCTION gold.security.region_access(region STRING)
  RETURNS BOOLEAN
  RETURN is_account_group_member('all-regions')  -- admins see all
      OR region = current_user();                 -- others see their region

-- Step 2: Apply to table
ALTER TABLE gold.sales.orders
  SET ROW FILTER gold.security.region_access ON (region);

-- Remove filter
ALTER TABLE gold.sales.orders DROP ROW FILTER;
Column Masks — control what values users see
SQL
-- Step 1: Create mask function
CREATE FUNCTION gold.security.mask_email(email STRING)
  RETURNS STRING
  RETURN CASE
    WHEN is_account_group_member('pii-access') THEN email
    ELSE concat(left(email, 2), '***@***.com')
  END;

-- Step 2: Apply to column
ALTER TABLE gold.customers.profiles
  ALTER COLUMN email SET MASK gold.security.mask_email;

-- Remove mask
ALTER TABLE gold.customers.profiles ALTER COLUMN email DROP MASK;
Row filter = SQL function returns BOOLEAN (true = show row). Column mask = SQL function transforms the column value. Both use is_account_group_member() or current_user() for dynamic logic. Both applied with ALTER TABLE.
High ABAC Tags, Data Lineage, Audit Logging & Delta Sharing ▾ expand
ABAC with Tags
  • Assign tags to catalogs, schemas, tables, columns: ALTER TABLE t SET TAGS ('pii' = 'true', 'domain' = 'finance');
  • Tags feed attribute-based policies — e.g., "mask all columns tagged pii=true" without needing to update each table manually.
  • Configure tag policies in the Databricks admin UI or via Unity Catalog API.
Data Lineage
  • Automatic for Delta tables. Shows in Catalog Explorer → Lineage tab.
  • Shows upstream sources and downstream consumers for any table.
  • Tracks: owner, history, dependencies, column-level lineage.
Audit Logging
  • Enable via workspace admin settings → Audit log delivery to ADLS Gen2.
  • Logs: who accessed what, when, which queries ran, permission changes.
  • Use Log Analytics to query audit logs (your DP-700 skill applies directly).
Delta Sharing
  • Open protocol to share Delta tables externally (across orgs, across clouds) without copying data.
  • Create a Share → add tables to it → create a Recipient → give recipient an activation link.
  • Recipient accesses data read-only using their own tools (Spark, Power BI, pandas).
Delta Sharing ≈ OneLake external shares in Fabric. You're sharing read access to data without copying it. The key difference: Delta Sharing is open protocol — recipients don't need Databricks.

Data Ingestion — All Methods

Prepare & Process 30–35%
Critical Auto Loader — Most Tested Ingestion Method ▾ expand
Nothing in ADF does exactly what Auto Loader does. The closest analogy is ADF's incremental copy with schema mapping — but Auto Loader is streaming, self-managing, and handles schema evolution automatically.
Python
# Auto Loader: incremental file ingestion as a stream
df = (spark.readStream
  .format("cloudFiles")                        # ← Always cloudFiles
  .option("cloudFiles.format", "json")           # ← Source file format
  .option("cloudFiles.schemaLocation",            # ← Where inferred schema is stored
           "/checkpoints/schema/events")
  .option("cloudFiles.inferColumnTypes", "true")  # ← Type inference
  .load("abfss://landing@stg.dfs.core.windows.net/events/"))

(df.writeStream
  .format("delta")
  .option("checkpointLocation", "/checkpoints/events")
  .option("mergeSchema", "true")                # ← Allow schema evolution
  .outputMode("append")
  .toTable("bronze.raw.events"))
Three Schema modes — know the difference
ModeBehaviourWhen to use
Schema inferenceAuto Loader infers schema from first batchUnknown schema, exploratory ingestion
Schema hintsYou provide hints, Auto Loader fills the gapsPartially known schema
Schema evolutionNew columns added to target table automaticallySource schema changes over time; set mergeSchema=true
Always specify BOTH schemaLocation AND checkpointLocation. Without checkpointLocation the stream cannot track progress. Without schemaLocation Auto Loader re-infers schema every restart (expensive).
High COPY INTO — Idempotent Batch Loading ▾ expand
SQL
-- COPY INTO: safe to re-run. Tracks loaded files internally.
COPY INTO bronze.raw.sales_events
FROM 'abfss://landing@mystg.dfs.core.windows.net/events/'
FILEFORMAT = JSON
FORMAT_OPTIONS (
  'inferSchema' = 'true',
  'timestampFormat' = 'yyyy-MM-dd HH:mm:ss'
)
COPY_OPTIONS (
  'mergeSchema' = 'true'  -- allow new columns
);

-- Also supports: CSV, PARQUET, AVRO, ORC, TEXT, BINARYFILE
  • Idempotent — tracks which files have been loaded. Re-running won't duplicate data.
  • Works on files in ADLS, S3, GCS or Unity Catalog Volumes.
  • Best for scheduled batch loads where files land periodically.
  • Use Auto Loader instead when you need continuous/streaming ingestion.
COPY INTO = batch, SQL-based, idempotent. Auto Loader = streaming, Python-based, continuous. The exam will give you a scenario and ask you to choose — batch scheduled? → COPY INTO. Continuous low-latency? → Auto Loader.
High Azure Event Hubs with Structured Streaming ▾ expand
You know Event Hubs from DP-700. In Databricks you consume it via the Kafka-compatible endpoint — Event Hubs exposes a Kafka protocol, so you use the Kafka connector in Spark.
Python
# Event Hubs via Kafka-compatible endpoint eh_conn = dbutils.secrets.get("kv-scope", "eventhub-conn-string") df = (spark.readStream .format("kafka") .option("kafka.bootstrap.servers", "mynamespace.servicebus.windows.net:9093") .option("subscribe", "my-event-hub") .option("kafka.security.protocol", "SASL_SSL") .option("kafka.sasl.jaas.config", f"...conn={eh_conn}...") .load()) # Parse JSON payload from Kafka value column from pyspark.sql.functions import from_json, col schema = "event_id BIGINT, amount DOUBLE, ts TIMESTAMP" parsed = df.select(from_json(col("value").cast("string"), schema).alias("data")).select("data.*")
Event Hubs uses the "kafka" format in Spark — NOT a dedicated Event Hubs connector. Always retrieve the connection string from Key Vault secrets. The value column in Kafka is binary — cast to string, then parse JSON.
High CDC — APPLY CHANGES INTO ▾ expand
ADF uses SQL Server CDC source connectors. Databricks handles CDC natively with APPLY CHANGES INTO inside Lakeflow Declarative Pipelines.
SQL — inside a Lakeflow Pipeline
-- APPLY CHANGES INTO handles INSERT, UPDATE, DELETE from CDC feed APPLY CHANGES INTO silver.customers.dim_customer FROM STREAM(bronze.raw.customer_cdc) KEYS (customer_id) APPLY AS DELETE WHEN operation_type = 'DELETE' SEQUENCE BY change_timestamp -- handles out-of-order events STORED AS SCD TYPE 1; -- or SCD TYPE 2
  • Only works inside Lakeflow Spark Declarative Pipelines — cannot run standalone.
  • KEYS = primary key column(s) to match on.
  • SEQUENCE BY = column used to order events (handles late-arriving changes).
  • SCD TYPE 1 = overwrite. SCD TYPE 2 = add new row, preserve history.
Medium Lakeflow Connect — No-Code Connectors ▾ expand
Lakeflow Connect = ADF's Copy Activity / Linked Services for SaaS sources, but built natively into Databricks. Same concept: click-based connector configuration, no custom code.
  • Connects to: Salesforce, ServiceNow, Google Analytics, SharePoint, databases, and more.
  • Supports both batch and streaming ingestion.
  • Data lands directly into Unity Catalog tables — no staging required.
  • Configure via Databricks UI → Data Ingestion → Lakeflow Connect.
When the exam asks "which tool to ingest from Salesforce into Unity Catalog with no code" → Lakeflow Connect. When it asks about file-based ingestion from ADLS → COPY INTO or Auto Loader.

Delta Lake — Advanced Patterns

Prepare & Process 30–35%
Critical OPTIMIZE, VACUUM, ZORDER & Liquid Clustering ▾ expand
SQL
-- OPTIMIZE: compacts many small files into larger ones (improves read perf) OPTIMIZE silver.sales.orders; -- OPTIMIZE with ZORDER: co-locate related data by column OPTIMIZE silver.sales.orders ZORDER BY (customer_id, order_date); -- VACUUM: delete files no longer referenced by Delta log VACUUM silver.sales.orders; -- default 7 day retention VACUUM silver.sales.orders RETAIN 168 HOURS; -- explicit 7 days -- DESCRIBE HISTORY: audit all operations on a table DESCRIBE HISTORY silver.sales.orders; -- Time travel SELECT * FROM silver.sales.orders VERSION AS OF 10; SELECT * FROM silver.sales.orders TIMESTAMP AS OF '2026-01-15'; -- Liquid clustering (modern alternative to ZORDER) CREATE TABLE gold.sales.orders CLUSTER BY (customer_id, order_date); -- Apply to existing table ALTER TABLE gold.sales.orders CLUSTER BY (customer_id);
CommandWhat it doesWhen to run
OPTIMIZEMerges small Parquet files into ~1GB filesNightly on high-write tables
ZORDER BYCo-locates rows with same key values in same filesWith OPTIMIZE for filtered queries on specific columns
VACUUMPhysically deletes Parquet files older than retention periodWeekly; never below 7 days retention if time travel needed
Liquid clusteringSelf-managing, incremental clustering. No full rewrites.New tables with multiple query patterns. Replaces ZORDER.
Deletion vectorsSoft-deletes: marks rows as deleted without rewriting Parquet filesEnabled by default on Databricks 14+. Improves DELETE perf.
Never run VACUUM RETAIN 0 HOURS in production — it breaks time travel and can corrupt streaming queries that reference old files. Minimum safe retention = 7 days (168 hours).
ZORDER = good for tables with 1-2 filter columns, static query patterns. Liquid clustering = better for tables queried on multiple different columns, or where query patterns change. Partitioning = only for very high cardinality date/region columns at massive scale.
High SCD Type 2 in Delta — MERGE Pattern ▾ expand
SQL
-- SCD Type 2: expire old row, insert new row MERGE INTO dim.dim_customer AS t USING ( SELECT *, current_timestamp() AS new_eff_start FROM staging.customers ) AS s ON t.customer_id = s.customer_id AND t.is_current = true -- Expire the current row if data changed WHEN MATCHED AND (t.name != s.name OR t.email != s.email) THEN UPDATE SET t.is_current = false, t.eff_end_date = current_timestamp() -- Insert changed rows as new current records WHEN NOT MATCHED THEN INSERT ( customer_id, name, email, eff_start_date, eff_end_date, is_current ) VALUES ( s.customer_id, s.name, s.email, s.new_eff_start, NULL, true );
In DP-750, SCD Type 2 is implemented either via manual MERGE (as above) or via APPLY CHANGES INTO ... STORED AS SCD TYPE 2 in a Lakeflow Pipeline. Know both patterns.

Lakeflow Spark Declarative Pipelines

Prepare & Process 30–35%
Critical Lakeflow Declarative Pipelines — @dlt Decorators & Expectations ▾ expand
Nothing in ADF/Synapse is equivalent. Lakeflow Pipelines is Databricks' declarative ETL framework (formerly Delta Live Tables). You define what you want, Databricks handles the execution order, dependencies, and data quality.
Python
import dlt from pyspark.sql.functions import col, current_timestamp # ── BRONZE: raw ingestion ────────────────────────────── @dlt.table( comment="Raw events from landing zone", table_properties={"quality": "bronze"} ) def bronze_events(): return (spark.readStream .format("cloudFiles") .option("cloudFiles.format", "json") .load("/Volumes/bronze/landing/events")) # ── SILVER: cleansed + quality checked ──────────────── @dlt.table(comment="Cleansed events") @dlt.expect("valid_event_id", "event_id IS NOT NULL") # WARN only @dlt.expect_or_drop("positive_amount", "amount > 0") # DROP bad row @dlt.expect_or_fail("valid_timestamp", "ts <= current_timestamp()") # HALT pipeline def silver_events(): return (dlt.read_stream("bronze_events") .filter(col("event_type").isNotNull()) .withColumn("ingested_at", current_timestamp())) # ── GOLD: aggregated ────────────────────────────────── @dlt.table def gold_daily_totals(): return (dlt.read("silver_events") # static read, not stream .groupBy("region") .sum("amount"))
The 3 Expectation Levels — memorise these
DecoratorOn failureUse when
@dlt.expectLog warning, keep the bad rowMonitoring only — don't want to lose data
@dlt.expect_or_dropDrop the bad row, continue pipelineFilter out invalid records silently
@dlt.expect_or_failHalt entire pipeline, raise errorCritical data quality — bad data must not proceed
Key rules to know
  • Use dlt.read_stream() for streaming sources, dlt.read() for batch/static.
  • Lakeflow Pipelines manage their own compute — you specify a pipeline cluster, not a job cluster.
  • APPLY CHANGES INTO is only available inside Lakeflow Pipelines.
  • Tables created by a pipeline are owned and managed by Unity Catalog.
The exam will give you a data quality scenario and ask which expectation type to use. Key: if the question says "alert but continue" → expect. "Discard invalid" → expect_or_drop. "Fail fast" → expect_or_fail.

Lakeflow Jobs, DABs & CI/CD

Deploy & Maintain 30–35%
High Lakeflow Jobs — Multi-Task Orchestration ▾ expand
Lakeflow Jobs = ADF Pipelines. Tasks = ADF Activities. depends_on = precedence constraints. You know this pattern — just learn the Databricks YAML/API format.
Key capabilities to know for the exam
  • Task types: notebook, Python script, SQL query, Lakeflow Pipeline, dbt, Spark JAR.
  • depends_on: defines task execution order (DAG). Multiple dependencies = all must succeed.
  • Repair run: re-run only failed/skipped tasks — does NOT restart successful tasks. Cost-efficient.
  • Job triggers: scheduled (cron), file arrival, continuous, manual.
  • Alerts: configure on start, success, failure, duration exceeded (SLA breach).
  • Automatic restart: configure max retries and retry interval on tasks or the whole job.
CLI — troubleshooting commands
# List recent runs databricks jobs run-now --job-id 12345 # Repair a failed run (re-run only failed tasks) databricks runs repair --run-id 67890 --rerun-all-failed-tasks # Cancel a running job databricks runs cancel --run-id 67890 # Get run output/logs databricks runs get-output --run-id 67890
Repair run vs restart: Repair = retry only failed tasks in an existing run (preserves successful task results). Restart = start a completely new run. Repair is always preferred for cost and speed.
Critical Databricks Asset Bundles (DABs) — CI/CD for Databricks ▾ expand
ADF deploys via ARM templates in Azure DevOps. Databricks deploys via DABs — YAML-defined bundles deployed through CLI or REST API. Same CI/CD concept, different format.
YAML — databricks.yml
bundle: name: sales_etl_bundle targets: dev: mode: development workspace: host: https://adb-111.22.azuredatabricks.net prod: mode: production workspace: host: https://adb-333.44.azuredatabricks.net resources: jobs: daily_etl: name: Daily Sales ETL job_clusters: - job_cluster_key: main new_cluster: spark_version: "15.4.x-scala2.12" node_type_id: Standard_DS3_v2 num_workers: 4 tasks: - task_key: ingest job_cluster_key: main notebook_task: notebook_path: ./notebooks/01_ingest.py - task_key: transform depends_on: [{task_key: ingest}] notebook_task: notebook_path: ./notebooks/02_transform.py
CLI — deployment commands to memorise
# Validate bundle config databricks bundle validate # Deploy to dev databricks bundle deploy --target dev # Deploy to prod databricks bundle deploy --target prod # Run a job from a deployed bundle databricks bundle run --target prod daily_etl
Know both deployment methods: CLI (databricks bundle deploy) AND REST API. The exam will ask which command to use. Bundle configs support environment-specific overrides via targets.

Spark Performance & Troubleshooting

Deploy & Maintain 30–35%
Critical Spark UI — Diagnosing Skew, Shuffle & Spill ▾ expand
Azure Monitor gives you job-level metrics. Spark UI gives you task-level internals. They complement each other — use Azure Monitor for alerting, Spark UI for root cause analysis.
IssueWhat it meansHow to diagnoseHow to fix
ShuffleData moved across network between executors (joins, groupBy, repartition)Spark UI → Stages → high "Shuffle Read/Write" sizeBroadcast small tables, reduce groupBy keys, use AQE
SkewOne partition much larger than others — one task runs 100x longerSpark UI → Stages → Tasks: max task duration >> medianrepartition(n, "key"), salting technique, AQE skew join
SpillExecutor runs out of memory, writes to disk (very slow)Spark UI → Stages → Spill column > 0Increase worker memory, reduce partition size, cache less
Python — performance fixes
# Fix skew: check partition distribution from pyspark.sql.functions import spark_partition_id df.groupBy(spark_partition_id()).count().show() # Fix skew: repartition evenly df_balanced = df.repartition(200, "customer_id") # Fix shuffle: broadcast join (small table < 200MB) from pyspark.sql.functions import broadcast result = large_df.join(broadcast(lookup_df), "id") # Enable Adaptive Query Execution (handles skew automatically) spark.conf.set("spark.sql.adaptive.enabled", "true") spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true") # Fix spill: cache only what's needed, unpersist when done df_hot.cache() df_hot.count() # trigger materialisation # ... use df_hot ... df_hot.unpersist()
Where to look in Spark UI
  • Jobs tab → see all Spark jobs and their status
  • Stages tab → see shuffle sizes, spill amounts, task distribution
  • DAG Visualization → see the execution plan as a graph (wide vs narrow transformations)
  • SQL / Query Profile → for SQL queries, see physical plan, bottlenecks, row counts per operator
The exam will describe a symptom and ask for the diagnosis tool and fix. "One task taking much longer" = skew → Spark UI Stages tab → repartition or broadcast. "Tasks writing to disk" = spill → increase memory or reduce data per task.
